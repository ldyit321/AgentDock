# AgentDock 文件存储、并发与上线设计

版本：v1.1评审稿｜2026-10-28。配套[主技术设计](AgentDock-技术设计-v1.1.md)。仅设计，未迁移文件、安装存储服务或改动用户配置。

## 1. 直接回答：D盘方案能否上线，需要锁吗

本地文件存储可以用于单机上线，不是只能演示。但需使用独立持久目录、容量控制、权限、备份及恢复验证，不能把文件写在重建后会消失的容器可写层。

多台应用服务器各有本地uploads会造成“这台上传、另一台读不到”，给文件加锁也不能让另一台机器获得字节。多节点部署建议对象存储或经过专门验证的共享文件系统。本MVP只做单机，但通过存储边界避免绑定D盘。

不需要给所有文件读写套一把锁。应将问题拆开：

| 内容 | 主要策略 | 是否需要文件锁 |
|---|---|---|
| 上传原件 | 系统生成唯一键，写好后只读 | 通常不需要为普通并行读取加锁 |
| 发布产物 | 每次生成新版本、新键，不覆盖旧内容 | 不需要多个写者竞争同一路径 |
| 工作快照 | 不可变清单及文件，ready后可读 | 通过发布协议，不边写边供读 |
| Sandbox工作文件 | 每Run独立，工具串行，修改前可校验hash | 由任务单写者和租约控制；后续若并行写同一路径才另设计细粒度锁 |
| 当前版本／最新快照指针 | MongoDB中version条件更新 | 需要并发控制，采用数据库CAS，而非磁盘全局锁 |
| 备份／清理 | 幂等作业、占用记录和删除状态 | 需要避免重复作业及与有效引用冲突，不靠简单读写锁包住一切 |

“不原地覆盖＋数据库管理版本”减少共享可变状态；并不意味着没有并发检查，也不意味着磁盘写入天然跨机器可靠。

## 2. 数据库与文件的职责

MongoDB存身份、对话、消息、Skill元数据、文件归属、版本、状态、索引、摘要和检查点。文件服务存图片、PDF、Office原件、提取文本、页图、脚本、日志和产物的字节。

用户选择MongoDB不等于所有二进制必须塞进数据库。BSON文档有大小限制，也不应无限追加大数组。GridFS可以作为另一个文件后端，但本期不默认采用，避免同时实现两套二进制存储。将来如果已有系统使用GridFS，可以评估新增适配器。

用户空间保留：公共Skill只读源区；每用户私有区；每对话uploads、workspaces、artifacts。对象存储里的前缀也可保留同样组织，但前缀不是权限系统，所有下载仍需服务端授权。

## 3. StorageProvider契约

业务层只使用FileRef，不使用`D:\...`或对象服务URL。建议字段：

| 字段 | 用途 |
|---|---|
| file_id、owner_user_id、conversation_id | 身份和归属 |
| provider | local／s3等实现标识 |
| namespace／bucket | 内部存储空间，不作为用户输入 |
| storage_key | 不透明逻辑键，系统生成 |
| object_version | 可选后端版本，不等于显示文件名 |
| sha256、size、media_type | 校验、容量和类型 |
| original_name、logical_path | 展示名称和恢复路径，规范化验证 |
| state、revision、created_at、deleted_at | 发布、变更和删除状态 |

最小接口：put_new、open_read、head、delete、copy_to_sandbox、import_from_sandbox。上传／下载返回流，不要求一次把全部文件读入内存。业务不直接调用Path操作目录，也不把任意user_id拼接成绝对路径。

LocalStorageProvider从配置的storage_root映射key；S3Provider映射bucket/key。模型只看到授权file_id和当前工作区相对路径，不看到服务端物理目录、凭据或永久公开URL。

## 4. 本地发布协议

1. 校验上传归属、类型与预留容量，创建files记录state=staging和唯一键。
2. 写同一持久文件系统中的临时文件；边写边限制字节、计算摘要，拒绝符号链接／越界路径。
3. 完成后关闭流，按平台要求flush并验证。发布到一个不会与其他请求复用的新最终键，不覆盖已有文件；使用独占创建或经过平台测试的不覆盖发布方式。
4. 文件完成后，在Mongo事务中把记录标ready、结算容量和写事件。只有ready可被其他请求引用。
5. 若落盘成功而数据库提交失败，留下可识别孤儿；若数据库已有staging而文件失败，标failed并回收预留容量。

同卷原子改名可以用于发布，但不是跨卷／跨网络文件系统通用保证。原子可见性也不等于突然断电必定不丢数据，可靠性仍依赖文件系统、持久卷与备份。启动时验证ready文件存在和摘要，损坏不伪装成功。

读取ready的不可变文件时，不需要与另一个普通读者互斥；写者使用不同键，读者不会看到半写内容。同名上传产生新file_id，名称只用于展示。

## 5. 工作目录与版本冲突

可变工作目录主要在Sandbox内，每Run独立，图工具按顺序执行。同一对话一个活动Run；进入等待前停止命令、保存快照并销毁实例；下一轮创建新实例恢复。

修改脚本使用expected_hash，当前内容不匹配就返回冲突，先重新读取，不静默覆盖。发布对话working_snapshot_id使用expected_version/expected_previous_snapshot条件更新，旧Worker不能用迟到结果覆盖新权威快照。

纯文本Run没有工作区变更时沿用原快照指针；本轮“无快照”不能写成空清单把旧成果清掉。成功终态清理前也要保存快照，失败／取消保存完整性，不冒称全量恢复。

如果将来增加同Run并行工具或多Run共享可写目录，需要重新设计锁粒度、持有者、过期和fencing；本版不靠引入Redis锁来提前解决尚未支持的共享写入。

## 6. 文件删除、下载和清理竞争

删除首先在数据库撤销访问并标deleting，不能仅删目录然后认为权限已处理。新下载被拒绝；已经发送出去的字节无法撤回，流正在传输时可按策略中断或允许收尾，不能承诺数据召回。

清理器只处理无有效快照／产物／活跃Run引用且达到保留期限的对象；引用检查与清理认领使用状态CAS和删除世代，不能“查一下没人用”后任意延迟删除。

文件一旦进入deleting，禁止新增引用；事务验证并登记引用，清理前复核状态和世代。物理删除幂等，失败保留状态重试；Mongo文档与磁盘／对象服务无法共同原子提交，依靠状态机和对账，不能承诺跨存储事务。

不可变Blob被多个本人引用时，区分逻辑file记录与物理对象引用，直到所有引用释放才清理；不跨用户全局去重。下载接口只用file_id，任何Range请求也鉴权，禁止把storage_root当静态资源目录发布。

## 7. 对象存储发布方式

线上多节点推荐S3兼容对象存储，但具体服务需用户选定，当前不安装。

- 用新key上传，不依赖目录rename或append；上传成功后校验size／自算sha256，再发布Mongo ready记录。
- 可以使用实现支持的条件创建防覆盖；不把ETag一概当文件MD5，分段上传／加密场景需分别验证。
- 未完成multipart上传要回收；文件引用仍由Mongo CAS管理，不在对象里维护一个经常覆盖的latest.json作为唯一真相。
- 下载可由后端代理，或鉴权后发短时签名URL；后者会暂时授权持有者，不能承诺删除后已签发URL立即失效。首版保持后端代理更简单。
- 不把AWS S3的一致性特性自动套给所有兼容实现；候选服务要测试发布、读取、覆盖和删除语义。[AWS S3一致性说明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)

对象存储也不能自动解决“两个写者覆盖同一个key”。本设计用新键和Mongo版本控制避免这种竞争，而不是把服务名称当锁。[S3条件写入](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)

## 8. 不同上线形态

| 部署 | 文件建议 | 前提／风险 |
|---|---|---|
| 当前Windows本机 | D盘持久目录 | API和Worker在同机，容量／权限／备份明确 |
| 一台正式服务器 | 独立持久磁盘或云盘挂载 | 服务重启后路径仍可用；非临时系统层 |
| 单机容器 | bind mount或受控persistent volume | 重建容器不删除数据，容器路径与主机路径分开 |
| 多API／多Worker机器 | 共享对象存储优先 | 任一节点可访问同一key；调度与恢复也需多节点设计，不只换存储 |
| NFS／SMB共享盘 | 可选，非默认 | 权限、锁、rename、缓存、一致性、吞吐均需单独验收 |

数据库也需要持久化与备份；Mongo副本集解决数据库高可用不自动备份本地文件，更不使API的D盘变成共享盘。

## 9. 从本地迁移到线上

1. 实现并验收目标StorageProvider，配置独立测试bucket／命名空间。
2. 导出迁移清单，限制新写或为迁移确定水位；现有不可变对象可在线复制，最终切换仍需对账。
3. 按file_id复制并核对sha256和size，记录每个对象的迁移结果。
4. 使用文件revision CAS更新provider／key／version，保留原位置作为有期限的回退引用；不能只全局改root配置。
5. 检查历史消息、快照、原图、解析页和产物都能读，才能回收旧位置。
6. 备份与还原演练同时覆盖Mongo、文件和凭据主密钥；定义一致水位和可接受恢复点。

仅在同一块D盘复制一份不构成磁盘故障容灾。正式上线应将备份放到独立故障域，并验证数据库索引引用与文件对象在同一恢复水位可用；具体异地／加密及保留期限在部署设计时确定。

未来云存储变化只替换适配和引用，不要求业务改成云盘路径。物理复制、验证和回退工作仍然存在，不能宣称“改一个配置就完成迁移”。

## 10. 必测项

相同文件名并发上传；staging中断；发布后Mongo事务失败；旧版本指针更新；删除与引用竞争；下载中撤销；快照不完整；容器重建保留；磁盘满；跨卷临时文件；迁移摘要不一致；多节点同对象读取；对象服务上传成功但响应丢失。检查结果与产品测试分开报告。

结论：MVP采用本地适配不妨碍未来上线；关键是持久化、独立文件键、元数据并发控制、权限与可替换边界。当前没有为用户创建共享存储、执行迁移或配置文件锁。
