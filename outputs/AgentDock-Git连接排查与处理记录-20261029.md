# AgentDock Git连接排查与处理记录

日期：2026-10-29。范围：当前Windows工程的GitHub连接和资料推送；不涉及产品研发。

## 1. 问题与已确认事实

此前Git推送分别遇到Windows schannel握手失败和OpenSSL unexpected EOF，设备授权工具也曾超时／断流。更换TLS后端没有解决历史故障，不能将其当作修复。

本轮检查发现：

- Windows系统代理已启用，地址为`127.0.0.1:7897`，对应端口处于监听状态。
- Git使用系统级schannel配置、Credential Manager，仓库此前未显式配置GitHub代理。
- Credential Manager现在可以列出账号ldyit321，说明当前已经存在可用账号登记，不需要用户再次反复授权。
- 当前直连和显式走系统代理的HTTP读取均成功，证书验证结果为0；Git读取远程main，两种路径各连续3次成功。
- 在本次代理配置前，远程main已包含资料提交e3c560b，与当时本地HEAD一致。不能把本次配置称为此前资料上传成功的原因。

**结论边界：**历史TLS故障属间歇性连接问题；当前网络已恢复，未能稳定复现。系统代理与Git显式连接配置存在差异，但上述证据不足以证明它是唯一根因。不能声称彻底根治所有网络故障。

## 2. 实际处理

已在当前仓库`.git/config`中配置GitHub专用代理：

```text
http.https://github.com.proxy = http://127.0.0.1:7897
```

它只影响本仓库对GitHub的HTTP连接，不改变其他仓库、全局Git或系统代理；保留原schannel后端，不关闭TLS证书验证。不修改认证令牌或将令牌放入URL／文件。

这里选择已经存在且验证通过的系统代理，固定当前工程的连接路径；不安装新代理，不修改用户代理服务。

## 3. 验证

配置后已实际执行`git push origin main`，返回`Everything up-to-date`；读取远程main与本地HEAD得到相同提交e3c560b84429216c6552ff5f9a74c0f879ab1597。这个结果证明本轮Git连接和推送检查成功，不表示此前错误从未发生。

本记录随后作为单独文档提交，再验证真实新增提交可以推送及远程提交一致；最终结果以Git历史和远程核对为准，不预填未来提交ID。

## 4. 跨环境与后续边界

本机代理配置在`.git/config`，不会随克隆传播。其他环境应按自身可用网络选择直连或代理，不能照抄本机127.0.0.1端口。代理停用后，这条显式配置会导致连接失败，需要重新检查当前环境，而不是要求反复网页登录。

若需撤销本次配置，可在当前仓库执行`git config --local --unset http.https://github.com.proxy`；这是回退说明，本轮没有执行撤销。

产品研发仍暂停。本轮只排查连接、配置本地Git和维护资料记录，不启动N01、不安装业务依赖或修改OpenSandbox。
