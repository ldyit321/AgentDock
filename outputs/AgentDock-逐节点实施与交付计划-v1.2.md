# AgentDock 逐节点实施与交付计划 v1.2

日期：2026-10-29。状态：**研发暂停；本计划待用户审阅，不构成开工授权。**

本文确定怎么逐步研发、每步交付什么，以及何时形成人工验收清单。需求和技术方向延续[主技术设计v1.1](AgentDock-技术设计-v1.1.md)；现行协作约束见根目录AGENTS.md第10节。原[开发任务细分](../docs/superpowers/plans/2026-10-29-agentdock-mvp.md)保留作技术拆分参考，不能覆盖本文的节点停靠与授权规则。

## 1. 本次修订解决的问题

此前计划给出了开发任务和测试，但没有充分区分“开发完成”“可以让用户验收”“用户已经验收”，也没有强制每步解释代码。本版采用**一个研发节点、一份交付报告、一次明确验收停靠**。

现在确定每节点的目标、边界、依赖和交付内容。**现在不冻结具体人工验收操作。**节点代码完成并完成开发验证后，结合实际实现再统计和编写可操作验收项；遇到实现变化、缺失界面或环境依赖，验收项随实际情况调整并解释，不能为了清单好看标通过。

未来节点的“验收方向”只帮助理解要检查什么，不是最终验收清单，也不表示该功能已实现。

## 2. 一个节点如何进行

1. **节点准备**：明确目标需求、设计依据、范围、不包含项、预期文件变化、依赖和风险；若需修订设计，先记录差异。
2. **用户明确开工**：例如“开始N01”。仅认可本计划，不启动产品代码、安装或服务。
3. **节点研发**：在授权范围内完成实现、必要测试和修复；用真实结果更新设计。节点内常规工作自主推进，不每条命令询问。
4. **开发自验与Review**：实际运行适当测试，检查失败路径、权限与可读性，处理发现；自查与独立审查分别注明。
5. **形成节点报告**：按实际实现统计需求／设计、自动验证、人工待验和Review结果，并补运行说明与代码讲解。
6. **用户验收停靠**：交付报告和可运行结果后停止推进下一节点。用户反馈问题时先修当前节点、更新报告；用户明确验收后才记录通过。
7. **下一节点授权**：只有用户明确表示开始下一节点才继续；可在同一句中“本节点通过，开始N02”，避免额外往返。

用户验收通过不等于自动批准上线、真实外部写入或正式归档。这些仍按已有范围授权和敏感操作规则处理。技术依赖满足后也不跳过人工停靠点。

**为什么前几个节点没有完整网页：**先验证影响全系统的基础机制，早期通过受限API、验证入口或报告验收；不把静态HTML演示当真网页。N12／N13才交付主要网页功能。若用户希望更早看到运行网页，应先调整顺序和依赖，不能默默超出当前节点。

**为什么N01可能没有业务代码：**它首先确认版本与恢复机制可行。可以交付验证代码和配置，但验证代码不能冒充生产能力；通过兼容性验证也不意味着多用户功能已完成。

## 4. 每节点必须交付的文档

报告路径约定：`outputs/implementation/Nxx-节点名称-交付报告.md`。只有实际开始该节点后才创建其报告；现在只提供[报告模板](AgentDock-节点交付报告模板.md)，不预先生成14份看似已完成的报告。

每份报告至少包含以下内容：

| 部分 | 必须回答的问题 |
|---|---|
| 本次范围与状态 | 用户授权了什么？本节点实际做了什么？哪些没做？是否仍有阻断？ |
| 需求完成统计 | 对应哪些稳定需求ID？每项实现程度、证据、剩余工作是什么？ |
| 设计落实统计 | 原设计哪些已经落成代码？哪些仍是文档？哪里改了设计，为什么？ |
| 自动验证 | 跑了什么、实际通过／失败／跳过多少、环境和证据是什么？ |
| 人工验收清单 | 根据本次真实实现，用户现在可以怎样操作、应看到什么、目前是否待验？ |
| 代码Review | 审查了哪些改动、以什么方式、发现哪些问题、哪些已修、哪些仍有风险？ |
| 代码理解过程 | 从一个实际入口跟踪输入、权限判断、业务、存储／外部调用与返回；关键文件和函数各负责什么？ |
| 使用和变更影响 | 怎样启动本节点结果、需要哪些本地配置、影响什么数据、怎样停止／回退？ |
| 结论与下一步 | 能否交用户验收？需要用户补什么？下一节点建议是什么？但不自动开始 |

阶段A～D完成时，另外输出`outputs/implementation/阶段A-完成情况汇总.md`等，汇总需求、设计、遗留项和人工验收状态，引用节点报告，不复制过时结论。

## 5. 完成统计怎么做

当前只统计文档和已存在SDK证据，**产品需求不能算完成**。以后按三张独立表记录：

1. **需求表**：需求ID／本节点子项／范围版本／实现状态／证据／剩余项。U编号是较粗需求，必要时建如`U04.N02.01`的可追踪子项；一个节点通过不能把整个U04多用户需求提前打满。
2. **设计表**：设计文档与章节／本次落实点／实际文件／验证状态／差异。静态设计已写和设计已被代码落实分开统计。
3. **验收与Review表**：人工验收待验／通过／未通过／受阻分别统计；Review问题按影响记录总数、已修、遗留及证据，不能只报“Review完成”。

实现状态、验证状态、人工状态分别列，不混成一个含糊的“完成”。例如实现已完成、测试已通过、人工仍待验是合法组合。统计项不随意拆分放大通过数量；变更分母时保留上版范围和原因。范围不稳定就逐项计数，不给百分比；提供百分比时必须同时给分母和排除项。

## 6. 节点完成后怎样形成验收清单

研发前先记录预期验证方向。研发后从实际入口和已完成需求中提取操作，再补失败、权限和恢复场景。每条包括：编号、关联需求、前置条件、实际入口、操作、预期、证据、是否需要用户参与、人工结果。

清单不能要求用户查看不存在的页面或运行未提供的脚本；需要Key／OAuth时仅说明本地配置，不索取聊天密钥。技术内部故障注入由研发完成，向用户提供可核查结论；不把必须理解底层数据库才能执行的操作全部推给用户。

首次提交统一标“待用户验收”，不能因为自动测试通过就改成人工通过。用户指出问题后更新清单和报告，保留失败与修复记录；无法运行的项标受阻而不是跳过后算通过。

## 7. 代码Review与代码理解的区别

**Review检查实现是否可靠。**按本节点真实风险检查归属、密钥、状态转换、并发、幂等、清理、错误、依赖和注释可读性。写出文件／位置、问题影响、处理和验证；没有独立审查就如实写“作者自查”。独立审查的安排不自动成为子Agent授权。

**代码理解帮助用户掌握做法。**每节点选一条已实现的典型路径，按“你做了什么→哪个入口接收→为何调用这个服务→如何校验／保存／执行→怎样返回结果→失败在哪里处理”讲解，附真实文件、关键函数和小型调用图。还要说明用户后续接入已有系统时可以复用哪个服务、哪些只是当前网页或适配器。当前没有产品代码，不虚构函数已存在。

中文注释15%按AGENTS口径检查；早期代码很少时说明范围和实际比例，不靠填充注释凑数。
